# 02 · 测试与评审规范

> 上位文件：[标准开发流程](../标准开发流程.md) §5、§8。

## 1. 测试分层

| 层 | 范围 | 要求 |
|---|---|---|
| 单元测试 | service 及以下的业务逻辑 | 不起 Spring 容器，毫秒级，随手可跑 |
| 集成测试 | api 层 HTTP 语义 | MockMvc 起真实上下文，覆盖路由、状态码、JSON 结构 |

骨架中的 `ProductServiceTest` / `ProductControllerTest` 即两类样板。

## 2. 命名与结构

- 用例命名：`方法_场景_预期`（如 `search_blankOrNull_returnsAll`）。
- 一个用例一个场景；断言失败信息要能定位到验收标准。

## 3. 必测情形

- 新增接口 / 新增业务分支逻辑 → 正常路径 + 边界 + 异常路径
- 修缺陷 → 必须附带能复现该缺陷的回归用例
- 覆盖率门槛：暂不设（最简载体，标记待定；引入时用 CI 强制）

## 4. 验收标准 ↔ 测试映射表（制度化）

**每个迭代的测试记录必须包含映射表**，逐条证明验收标准被验证（先例：迭代 001 测试记录）：

```
| # | 验收标准 | 验证方式 | 结果 |
|---|---|---|---|
| 1 | <标准原文> | <用例名/手工方式> | ✅ |
```

来源：迭代 001 复盘第 3 条——该表曾在自检中抓到"验收标准 2 无测试覆盖"。

## 5. 评审流程

1. 开发方（人或 AI）完成 §5.1 自检清单，结果如实记入迭代档案；
2. 人按 §5.2 清单评审，材料 = 迭代档案 + `git diff main`；
3. 每条意见必须闭环（已修改，或说明不改的理由）后才可合并；
4. AI 声称的"通过"不算数，以门禁实际执行结果为准（总纲 §6）。
