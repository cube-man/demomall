# 01 · 分支与版本管理

> 上位文件：[标准开发流程](../标准开发流程.md) §8 配套规范。
> 适用：单人 + AI 开发模式；团队扩大时重审本文。

## 1. 分支模型（简化 GitHub Flow）

- `main` 是唯一长期分支，永远处于可用状态（CI 绿）。
- 功能/修复走短命分支，命名 `<类型>/<简称>`：如 `feat/product-search`、`fix/login-null`。
- 合并用 `git merge --no-ff`，保留分支痕迹（先例：迭代 001）。
- **不设** develop / release / 多人长期分支——单人+AI 模式下它们只增加成本。

## 2. 提交信息（Conventional Commits）

格式：`<type>: <主题>`，需要时追加 body。

- type 取值：`feat` / `fix` / `docs` / `refactor` / `test` / `chore` / `ci` / `merge`
- 主题一行说清"改了什么"；body 回答门禁第 3 条的三问：改了什么、为什么、怎么验证的。

示例（取自真实历史）：

```
feat: 商品按名称搜索接口（迭代 001）

新增 GET /api/products/search?name=：空参数返回全部，匹配不区分大小写；
验收标准 5/5 通过，mvn verify 12/12 全绿；README 与架构说明已同步
```

## 3. 版本号（SemVer）

- 开发期：`0.x.0-SNAPSHOT`（0.x 阶段=接口可能随时变）。
- 对外可用后升 `1.0.0`；语义：主版本.次版本.修订号，破坏/新增/修复各自升位。

## 4. 发版与 tag

- 发版动作：CHANGELOG 的 `[Unreleased]` 改为版本段落 → pom 去 SNAPSHOT → 提交 → `git tag v0.1.0` → push（含 `--tags`）。
- tag 仅在发版时打，命名 `v<版本号>`；CI 绿是发版前提（门禁第 1 条）。
