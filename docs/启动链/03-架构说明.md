## 形态

**单模块分层单体**（Spring Boot 2.7 / Java 8）。刻意不做多模块：载体追求最简，多模块是复杂度，本样板不演示。

## 模块划分（包结构）

```
com.demomall
├── api        接口层：Controller、请求/响应 DTO、参数校验
├── service    业务层：业务逻辑（纯逻辑，可被单元测试直接覆盖）
├── infra      基础设施：配置类；未来的外部访问实现（当前近乎为空）
└── DemomallApplication
```

## 依赖规则（红线）

1. `api → service → infra`，**禁止反向依赖**；
2. api 层不写业务逻辑，只做参数校验与 DTO 转换；service 层不依赖 HTTP 技术；
3. 跨层传值各用各的 DTO，内部模型不直接抛给接口层。

## 示例业务（迭代循环的演示载体）

**商品目录**：内存预置若干商品，暴露两个接口——

- `GET /api/products` 商品列表
- `GET /api/products/{id}` 商品详情

启动即用，无存储。启动链完成后，第一个迭代改动从这里开始（候选：按名称搜索），用它走通 §2 全循环。

## 关键数据流

请求 → api（校验/转换）→ service（业务逻辑）→ 响应 DTO → JSON

## 技术风险与对策

| 风险 | 对策 |
|---|---|
| 内存数据重启即失 | 已接受（边界内）。引入存储时首推 H2，届时更新本表 |
| 接口无鉴权 | 已接受：仅限本机运行。若未来给他人用，列入迭代候选再补 |
| 并发 | 无要求。内存数据用不可变结构，不做优化 |
| 可测试性 | service 纯逻辑可单元测试；api 层用 MockMvc 集成测试——骨架自带两类示例测试各一条 |
